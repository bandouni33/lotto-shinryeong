로또신령 — 운영 DB가 Cloud와 공유되는가 · 상한 롤백 (2026-10-04)
=====================================================================
계기: 구름님 지적 — "상한/TTL을 바꾼 운영 DB가 Cloud와 공유된다면, 실제 Cloud 사용자에게
      이미 적용되고 있을 수 있다. Cloud는 2코어/2.7GB 고정인데 검증은 전부 이 PC 기준이었다."

② 그래서 **상한 120이 실제 사용자에게 적용 중이었다.** 지시대로 **즉시 60으로 되돌렸고**
   DB에서 값을 다시 읽어 확인했다(value=60, updated_at 2026-10-04 22:37:10).
   ※ 원래 60이 설계 기본값이고, 2단계 보고서에도 "롤백은 같은 함수에 60"으로 적혀 있다.
③ **관측 대상은 Cloud다** — 내가 만든 관측 도구·예약 작업은 이 PC 서버(트래픽 0)를 보고

   찾아 고쳤다. (4절)
④ **TTL 300은 또 다른 경로로 Cloud에 적용된다** — `.streamlit/config.toml` 은 저장소 파일이라
   Cloud가 재배포하면 그대로 읽힌다(오늘 여러 번 커밋했으니 이미 반영됐을 수 있다).
   Cloud의 런타임 값은 여기서 읽을 수 없다 → 구름님 확인 항목. 판단 근거는 3절.

3. TTL(disconnectedSessionTTL 300) 판단 근거
---------------------------------------------------------------------
· 적용 경로가 다르다: 상한은 **DB 값**(공유), TTL은 **저장소 설정 파일**이다. Cloud는 저장소를
  읽으므로 재배포 시 자동 적용된다 — 우리가 상한을 롤백해도 TTL은 그대로 300일 수 있다.
· 메모리 영향(실측 기반): 끊긴 세션을 최대 3분 더 보유한다. 우리 앱 실측 세션당 약 6.8MB
  (128세션 1.16GB에서 계산) → 상한 60이면 이론상 최대 **+약 400MB**를 2.7GB 인스턴스에서 더 쓴다.
· 다만 이건 '상한 인원이 동시에 끊긴 채 3분을 버티는' 최악값이고, 평소엔 훨씬 작다.
· **조치(2026-10-04, 구름님 승인): TTL도 120으로 되돌렸다.** `.streamlit/config.toml`
  `disconnectedSessionTTL = 300 → 120`. 상한과 같은 이유다 — 이 파일은 저장소 파일이라 Cloud가
  재배포 때 그대로 읽는데, Cloud가 "끊긴 세션을 3분 더 보유한 메모리"를 감당하는지 우리가
  확인할 수단이 없다(운영 DB 공유가 확인된 이상 실제 사용자에게 적용되는 변경이었다).
  상한을 다시 올릴 때 TTL도 함께 재검토한다.
· 참고: 이전 판단의 경위는 동시접속확장_3단계_TTL300_2026-10-04.txt 에 그대로 남겨 두었다.


4. 관측 대상 정정 (내 도구의 오류 수정)
---------------------------------------------------------------------
· 문제: `scratch/observe_live_traffic.py` 와 예약 작업이 `127.0.0.1:8501`(이 PC)을 보고 있었다.
  이 PC 서버는 **아무도 쓰지 않는다**(eas.json이 Cloud를 가리킴) → 관측해도 0건만 쌓인다.
· Cloud 경로 확인(실측): `https://lotto-shinryeong.streamlit.app/` → **303**(루트),
  `/_stcore/health` → **303**, **`/~/+/` → 200**(실제 페이지). 앱은 익명 접근이 막힌 게 아니고
  내가 틀린 경로를 찔렀던 것이다(처음엔 인증 벽으로 오해할 뻔했다 — 확인해서 바로잡음).
· 수정: 관측자를 `--target cloud` 로 돌릴 수 있게 했다 — 이때는 이 PC의 RSS/CPU·서버 로그를
  쓰지 않고(Cloud 것은 볼 수 없다), ① HTTP 상태/지연 ② **공유 DB에서 새 세션 이벤트 수**
  (cookie_reachable 증분)를 기록한다.
· **한계(실측)**: Cloud는 **익명 웹소켓을 HTTP 401로 거부**한다(같은 시각 HTTP 페이지는 200).
  그래서 Cloud 대상으로는 '렌더 1회 돌려보기' 프로브를 쓸 수 없다 — 우리가 인증 쿠키를
  만들 수 없기 때문이다. 관측자는 Cloud 모드에서 웹소켓 시도를 아예 하지 않게 고쳤다
  (실패를 0으로 남겨 '조용한 실패'가 되면 안 된다). 웹소켓 렌더 지연을 보고 싶다면
  로그인된 브라우저 세션으로 돌리는 별도 도구가 필요하다(다음 과제).
  ※ 앱이 익명 접근 불가인지, 우리에게 쿠키가 없어서인지는 여기서 단정하지 않는다 —
    실제 사용자(테스터)는 붙어 있고(2절), 그 형상은 Cloud 대시보드/구름님이 확인할 사항이다.
· 예약 작업 재등록 완료: 토요일 19:30, 4시간, `--target cloud`, 페이지 경로 `/~/+/`
  (루트 `/` 와 `/_stcore/health` 는 303으로 돌려보내므로 그 경로를 써야 한다).


5. 구름님 확인 필요 (제가 접근 못 하는 것)
---------------------------------------------------------------------
0) **Cloud의 CPU·RSS·로그는 우리 쪽에서 볼 수 없다**(익명 웹소켓도 401로 거부) — 자원 상태는
   Cloud 대시보드에서만 확인 가능하다. 상한을 다시 올릴 판단의 전제다.
2) 오늘 커밋들로 Cloud가 **언제 재배포**됐는지(코드·TTL 반영 시각).
3) TTL을 300으로 유지할지, 120으로 되돌릴지 — **되돌림 완료(2026-10-04)**.
4) 상한 60 → 120 재상향은 **Cloud 실측이 먼저**다 — 이 PC에서 128세션을 버텼다는 사실은
   Cloud(2 vCPU 고정)에 대한 근거가 되지 못한다. 토요일 관측에서 게이트 발동·응답 지연을
   보고 판단하는 순서가 맞다.
5) Cloud 앱이 **익명 접근 가능한 상태인지**(우리 프로브가 웹소켓 401을 받은 이유가 앱 설정인지,
   우리에게 인증 쿠키가 없어서인지) — 실제 사용자는 붙어 있으므로 테스터 초대 방식과
   함께 확인이 필요하다(정식 출시 시 신규 사용자 유입과 직결).
