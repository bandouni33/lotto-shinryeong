로또신령 — 동시접속 확장 3단계: disconnectedSessionTTL 120 → 300
=====================================================================
작성 2026-10-04 · 승인: (C) 지금 바로 진행 (구름님 지시)
사안: 웹소켓이 끊긴 세션을 서버가 붙들고 있는 시간을 120초 → 300초로 연장
영향 범위: 설정 1줄 + 서버 재시작. 앱 코드·DB·상한값은 건드리지 않았다.


1. 결론
---------------------------------------------------------------------
· 설정 한 곳(.streamlit/config.toml 의 [server] 표)에만 값을 넣었다.
· Streamlit 자신의 로더로 300이 해석되는 것을 확인했고, **설정이 없는 격리
  디렉터리에서는 120(기본값)** 이 나오는 것까지 대조했다. 즉 300은 이 저장소
  파일 때문이다.
· 이 값을 덮어쓸 수 있는 다른 곳(서버 실행 .ps1 의 CLI 플래그, 다른 설정/JSON/파이썬
  파일)은 없다 — "기준점은 한 곳" 규칙이 유지된다.
· 적용에는 재시작이 필요하므로 운영 서버를 재시작했다(수 초 다운타임). 새 프로세스가
  설정 변경 **이후**에 기동했으므로 새 값으로 동작한다.
· 대가는 메모리다(끊긴 세션을 최대 3분 더 보유). 아래 4절에 수치로 적었다.


2. 무엇을 왜 바꿨나
---------------------------------------------------------------------
값의 뜻: Streamlit은 웹소켓이 끊긴 세션을 곧바로 버리지 않고
`server.disconnectedSessionTTL` 초 동안 보관한 뒤 정리한다. 기본값 120초
(venv312\\Lib\\site-packages\\streamlit\\config.py 의 default_val=120).
모바일은 화면을 벗어나면 웹소켓이 끊기므로, 2분을 넘겨 돌아온 사용자는 세션이
사라져 화면을 처음부터 다시 그려야 했다(재렌더·DB 재조회 비용).
300초로 올려 "잠깐 앱을 벗어났다 돌아오는" 흐름의 비용을 줄인다.

바꾼 곳 — 한 곳뿐이다:
  .streamlit/config.toml   [server] 표 안에  disconnectedSessionTTL = 300
  (값 옆에 왜·대가·되돌리는 방법을 주석으로 함께 남겼다)


3. 검증 (실제로 돌린 것)
---------------------------------------------------------------------
검증 1 — 기준점이 한 곳이고 [server] 표 안인가
  · 값 줄이 파일에 정확히 1개, 내용이 그대로인지 확인
  · tomllib 으로 파싱해 [server] 표 안에 있는지 확인(표 밖에 두면 Streamlit이 무시한다)

검증 2 — 서버가 쓰는 경로로 300이 나오는가 (파일만 보고 말하지 않는다)
  · 서버 기동 시 부르는 것과 같은 함수로 해석:
      streamlit.web.bootstrap.load_config_options({...}) → config.get_option(...)
  · 이 저장소에서       : 300
  · 설정 없는 격리 임시 디렉터리에서 : 120  ← 대조군(기본값)
    → 값의 출처가 이 파일임을 확정

검증 3 — 덮어쓰는 곳이 없는가
  · run_server.ps1 · keep_server_up.ps1 · register_server_task.ps1 에
    --server.disconnectedSessionTTL 플래그 없음
  · 저장소의 .toml/.json/.py/.ps1/.ini/.cfg 중 이 값을 설정하는 파일 없음
    (주석에 언급된 줄은 제외 — 실행에 영향이 없다)

검증 4 — 적용 후 서버가 실제로 살아 있는가 (재시작 직후)
  · 재시작 전 PID 20296 → 재시작 후 PID 25980 (포트 8501 LISTENING)
  · http://127.0.0.1:8501/?page=main → HTTP 200
  · 웹소켓 세션 1개로 실제 렌더 1건: 성공, script 3,702ms (콜드), 실패 0건
  · 새 프로세스는 설정 변경 이후에 기동했으므로 새 값을 읽었다

테스트 파일: tests/test_session_ttl_300.py (위 1~3 + 아래 6절 보고서 조건을 고정)


4. 대가와 리스크 (숨기지 않는다)
---------------------------------------------------------------------
· 대가: 끊긴 세션의 메모리를 최대 300초(기존 120초) 보유한다.
  실측 세션당 증가분 약 3.2MB(2026-10-04 1단계 조사) → 상한 인원(120명)이
  동시에 끊긴 채 남는 최악의 경우 이론상 최대 약 384MB 추가 보유.
  이 PC(16GB, 여유 6.9~7.1GB)에서 감당 가능한 크기지만, 상한을 더 올릴 때
  (150~200) 이 항목이 함께 커진다는 점은 기억해야 한다.
· 위 384MB는 **상한값과 세션당 실측치로 계산한 상한선**이지 측정값이 아니다.
· 세션 ID를 재사용하는 재연결이 프록시를 거칠 때는 세션 고정(sticky)이 필요하다.
  현재는 단일 인스턴스 직접 접속이라 해당 없음(부하분산 도입 시 재검토 항목).


5. 되돌리기 (문제가 생기면)
---------------------------------------------------------------------
· .streamlit/config.toml 에서 `disconnectedSessionTTL = 300` 줄을 삭제 → 기본 120
· 서버 재시작(설정은 기동 시에만 읽는다)
    powershell -NoProfile -ExecutionPolicy Bypass -Command "Stop-Process -Id (Get-NetTCPConnection -State Listen -LocalPort 8501).OwningProcess -Force"
    powershell -NoProfile -ExecutionPolicy Bypass -File .\keep_server_up.ps1
· 재시작은 작업 스케줄러(LottoShinryeongServer, 5분 주기)도 자동 복구한다
  — 위 watchdog 을 안 불러도 5분 안에 다시 뜬다.


6. 미검증 (다음에 확인할 것)
---------------------------------------------------------------------
· **세션 보유 시간 자체(300초)는 직접 계측하지 않았다.** Streamlit 내부 정리
  동작이고 외부에서 관측할 지점이 없다. 확인한 것은 "설정 파일이 300으로 해석된다" +
  "새 프로세스로 재시작했다"까지다. 억지로 재려면 서버 로그에 내부 정리 시각을
  찍는 코드를 넣어야 하는데, 그건 제품 코드를 검증용으로 바꾸는 일이라 하지 않았다.
· 모바일 실기기에서 "앱을 3분 안에 다시 열면 로그인·화면 상태가 유지되는가"는
  실기기 QA 항목이다(안드로이드·iOS 각각).
· iOS 실기기 검증은 아직 한 번도 없다(iOS 업데이트 빌드 작업에서 함께 확인).
